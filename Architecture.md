# Архитектура Pairspace

Статус: целевая архитектура, не утверждение о готовом backend. База: ccbe5df.

## Решения
1. Один мобильный код Expo/React Native/TypeScript для iOS и Android.
2. Существующий Next.js интерфейс остаётся отдельным веб-концептом и референсом.
3. Начать с модульного монолита backend и PostgreSQL, не с микросервисов.
4. Объектное хранилище закрытое; подписанные URL короткоживущие после проверки ACL.
5. Realtime доставляет события; долговечная БД является источником истины.
6. Transactional outbox для событий и уведомлений; повторная обработка безопасна.
7. Провайдеры auth, БД, realtime и push закрыты адаптерами. До выбора рынка и бюджета не подключать платные сервисы.

## Предлагаемая структура, пока не создана
- apps/mobile: маршруты, композиция экранов и platform adapters.
- packages/domain: чистые правила пары, писем, чата, календаря и расходов.
- packages/contracts: схемы команд/ответов/событий и версии.
- packages/ui: тема, доступные компоненты, состояния.
- packages/i18n: RU/EN словари и форматирование.
- services/api: session/authz, use cases, repositories, HTTP/realtime.
- services/worker: outbox, уведомления, обработка файлов, удаление.

Разносить каталоги постепенно, не создавать пустой monorepo ради схемы.
В каждом модуле: domain → application → adapters; UI вызывает use cases, а не БД.

## Поток записи
Клиент создаёт command_id → сервер проверяет сессию и членство → валидирует схему →
в транзакции пишет ресурс и outbox → возвращает подтверждение → worker публикует событие.
Повтор command_id возвращает прежний результат, не дублирует запись.
Конкурирующие изменения используют expected_version; конфликт нельзя молча перезаписать.

## Время и offline
- Хранить события как UTC instant, календарные даты отдельно, IANA zone явно.
- Доступ к запечатанным письмам определяется сервером, не часами телефона.
- Offline очередь ограничена по размеру, очищается при logout/отвязке.
- Черновики приватны автору. Ресинхронизация по cursor с повторной авторизацией.
- Резервная копия и восстановление проходят отдельное испытание, не только успешный backup job.

## Нефункциональные цели для измерения
Начальный целевой p95 API без upload: <500 мс; realtime доставки онлайн <2 с при штатной сети.
Это цели staging-нагрузочного теста, не установленный SLA. 24/7 означает отсутствие временных ограничений общения.
До запуска выбрать нагрузочный профиль, регион хранения, RPO/RTO и дежурство.
Наблюдаемость: latency, error rate, backlog, reconnect, duplicate rate без содержимого сообщений.
