# Правила разработки Pairspace

## Назначение и границы
- Продукт для множества независимых пар. Общение с владельцем проекта по-русски.
- Основной мобильный клиент: Expo / React Native / TypeScript, iOS и Android, RU/EN.
- Текущий Next.js концепт сохранять как референс. Не объявлять его мобильным клиентом.
- Исходный Tan Ata изучать по коду; не менять его production и не переносить личные данные.
- Работать в облаке. Компьютер владельца, его процессы и локальные файлы не использовать.
- Не переписывать историю и чужие коммиты. Отдельная ветка, небольшие тематические коммиты.
- Публикация, слияние, развёртывание и платные сервисы являются разными действиями.
- Для каждого изменения читать инструкции каталога и связанные спецификации.
- До изменения Next.js читать документацию соответствующей установленной версии.

## Читаемость
- Не более 600 строк в каждом рукописном файле, включая тесты и документы.
- Исключение: машинные lockfile, сгенерированные типы/артефакты с указанным генератором.
- Не минифицировать код ради лимита. Разделять по ответственности и публичным контрактам.
- Строгая типизация, явные состояния ошибок, никаких any ради подавления проверки.
- Доменная логика не зависит от React Native, БД или провайдера уведомлений.
- Новая зависимость требует проверки лицензии, поддержки, уязвимостей и необходимости.
- Не копировать чужие бренды, иллюстрации, тексты, приватные API и закрытый код.

## Приватность
- Пользователь и пара имеют независимые ID; пол не определяет доступ и оплату.
- Каждый приватный ресурс связан с couple_id; сервер проверяет членство и полномочия.
- Тестировать пары A и B, бывшего участника, неавторизованного клиента и фоновые задания.
- Не хранить секреты в Git, публичных EXPO_PUBLIC переменных и логах.
- Не передавать тексты писем/чата в аналитику, crash reports и push по умолчанию.
- Не обещать E2EE до реализации и независимой проверки протокола и ключей.
- ИИ получает лишь явно разрешённые источники; никогда чужие черновики и закрытые письма.
- Не использовать настоящие данные пары в тестах и демо.

## Обязательная проверка
- Писать тесты одновременно с функцией, включая ошибки и повторные запросы.
- Цель блокировки CI: ≥90% statements, branches, functions и lines всего собственного production-кода.
- В coverage включать неимпортированные тестами файлы. Исключения перечислять поимённо и обосновывать.
- Пройденные unit-тесты не заменяют интеграцию, E2E и проверки двух устройств.
- Изменённые UI проверять на iOS/Android, RU/EN, offline, повторное нажатие и interrupted flow.
- Независимый reviewer проверяет точный SHA, требования, diff, тесты и ограничения.
- До независимой приёмки статус «не принято». Автор не может принять свою работу.
- Исправления после приёмки требуют повторной проверки затронутых сценариев.
- Указывать отдельно: прошло, упало, не запускалось. Не выдавать export JS за native build.
