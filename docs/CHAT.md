# Приватный чат пары: спецификация

Статус: план реализации, восстановленный 10 ноября 2026 года по доступным требованиям.
В `main` на `ccbe5df` есть веб-концепт, но нет работающего сервера чата,
авторизации, синхронизации, push или проверенного шифрования переписки.
Этот документ не является отчётом о готовности этих функций.

## Ограниченная реализация, 10 ноября 2026

Opt-in synthetic loopback поддерживает RAM-only draft и одну immutable команду с
явным retry; см. [CHAT_RECOVERY](../apps/mobile/CHAT_RECOVERY.md). Подтверждение только
серверное, не delivery/read. Transient discovery сохраняет draft лишь внутри уже
проверенного сеанса; auth/scope/logout/unmount очищают всё. Перезапуск процесса теряет
RAM. Описанные ниже durable offline queue, приостановка после истечения сессии,
квитанции и два устройства остаются целевым планом, а не свойствами этого шага.

## Задача и границы

Пара общается внутри приложения в любое время, с привычной механикой мессенджера.
«Как Telegram» означает удобство переписки, а не совместимость с Telegram,
копирование бренда или обещание всех его функций. «24/7» означает отсутствие
продуктовых часов работы; абсолютная доступность не гарантируется.
Один общий диалог на одну пару. Не нужны поиск чужих пользователей, каналы,
группы, реклама в переписке и публичный каталог пар.
Клиент: Expo для iOS/Android; все состояния и ошибки доступны на русском и английском.
Чат и письма остаются разными сущностями: письмо может быть запечатано до даты,
обычное сообщение показывается после принятия сервером.

## Объём

### P0: до внешнего пилота

- Независимый аккаунт каждого человека; безопасное объединение двух участников.
- Текст, переносы строк, emoji; лимит 8 000 Unicode code points после нормализации NFC.
- Отправка, история с постраничной загрузкой, ответ на сообщение, копирование текста.
- Статусы «Отправляется», «Отправлено», «Доставлено», «Прочитано», «Не отправлено».
- Черновик и очередь исходящих на устройстве; повтор без дублей после восстановления сети.
- Исправление своего текста и удаление своего сообщения у обоих с явным подтверждением.
- Скрытие сообщения только у себя; настройка уведомлений и отметок прочтения.
- Разделение аккаунтов/пар на сервере, в подписках realtime, кэше и фоновых задачах.
- Безопасный выход, отзыв устройства, завершение пары, экспорт и удаление аккаунта.
- Центральное «Думаю о тебе» сохраняется отдельным действием заботы, не заменяет чат.

### P1: после стабильного текста

Фото, голосовые сообщения, реакции, поиск, закрепления, индикатор набора.
Вложения требуют приватного хранилища, проверки типа/размера, удаления метаданных
геолокации по умолчанию и отдельной приёмки доступа. Не показывать неработающие кнопки.
Видео/аудиозвонки и сложная синхронизация нескольких устройств оцениваются отдельно.
Переход к E2EE регулирует [SECURITY.md](../SECURITY.md); без этого не обещать
«никто, даже сервис, не может читать сообщения».

## Основные сценарии

1. Пока партнёр не принял приглашение, показывать объяснение, а не фиктивный диалог.
2. При двух активных участниках открывать историю с последним прочитанным местом.
3. Отправка сразу создаёт локальный элемент `queued`; текст очищается лишь после
   сохранения записи в локальную очередь. Кнопка отправки не создаёт второй ID при повторе.
4. Сервер подтверждает транзакцию: элемент получает `server_id`, `seq`, `created_at`.
5. Получатель получает событие либо догружает историю; подтверждение сохранения клиентом
   обновляет «Доставлено». Push-ответ провайдера не является доставкой сообщения человеку.
6. Видимый активный экран отправляет отметку прочтения только с включённым разрешением.
   Открытие push или фоновая загрузка сами по себе не означают чтение.
7. При потере связи показывать честный офлайн-статус и очередь. После переподключения
   сначала проверить сессию/членство, затем синхронизировать и отправить очередь.
8. Если членство отозвано, очередь останавливается: старые сообщения нельзя отправить
   новому партнёру. Пользователь может удалить локальные неотправленные записи.
9. При редактировании другим устройством запрашивается актуальная версия; конфликт
   нельзя автоматически затереть. Удаление побеждает последующую устаревшую правку.
10. Если собеседник удалил исходное сообщение, ответ показывает «Сообщение удалено»,
    а не сохранённую в цитате копию исходного приватного текста.

## Контракт API v1

Все пути относительны к отдельному API нового продукта. HTTPS обязателен.
Автор определяется сессией; тело запроса не может назначать другого `sender_id`.
`couple_id` из пути проверяется по текущему активному членству в каждой операции.

- `GET /v1/couples/{id}/chat/messages?before={opaque_cursor}&limit=50`:
  история, не более 100 записей, сортировка по серверному `seq`.
- `POST /v1/couples/{id}/chat/messages`: `{client_message_id, body, reply_to_id?}`;
  заголовок `Idempotency-Key`; ответ 201 с канонической записью, 200 при точном повторе.
- `PATCH /v1/couples/{id}/chat/messages/{message_id}`:
  `{body, expected_version}`; авторство и версия обязательны.
- `DELETE /v1/couples/{id}/chat/messages/{message_id}`:
  `{scope: "everyone", expected_version}`; только автор, tombstone вместо текста.
- `PUT /v1/couples/{id}/chat/messages/{message_id}/hidden`:
  `{hidden: true}`; видимость меняется только для текущего участника.
- `PUT /v1/couples/{id}/chat/receipts`: `{delivered_seq?, read_message_ids?}`;
  delivered_seq монотонен и не выше доступного seq; read_message_ids содержит только
  сообщения партнёра, реально показанные после включения квитанций (максимум 100 за запрос).
- `GET /v1/couples/{id}/chat/sync?after={event_cursor}`:
  изменения, удаления и новый курсор; недействительный старый курсор требует полной синхронизации.
- `PUT /v1/me/chat-preferences`: `{read_receipts_enabled, notifications_enabled}`.

Ответ сообщения: `id`, `couple_id`, `sender_id`, `client_message_id`, `seq`,
`body` либо `null` для удаления, `reply_to_id`, `version`, `created_at`, `edited_at`,
`deleted_at`. Приватный текст не попадает в URL, ошибки, метрики или трассировку.
Ошибки: 401 сессия истекла, 404 ресурс отсутствует/недоступен, 409 конфликт версии
или повтор ключа с другим содержимым, 422 неверное тело, 429 ограничение с Retry-After.
После разрыва пары допустим 403 с нейтральным кодом `membership_inactive` для собственной
ранее известной пары; чужие идентификаторы не раскрывают существование ресурса.

## Состояния и идемпотентность

Локальное исходящее: `draft → queued → sending → accepted`.
Из `sending` при таймауте возвращаемся в `queued`, сохраняя тот же UUID/ключ;
при окончательном 4xx переходим в `failed`, показываем причину и доступные действия.
Истечение сессии приостанавливает очередь, а не уничтожает её как ошибочный ввод.
«Отправлено» показывается только после ответа или синхронизации канонической записи.
`accepted → delivered → read` описывает подтверждения получателя, не состояние сети.
Удаление хранится отдельным признаком и не откатывается квитанциями.

Уникальность `(couple_id, sender_id, client_message_id)` в БД обязательна.
Idempotency-Key привязан к пользователю, операции и хешу тела; совпавший ключ с
другим содержимым даёт 409. При точном повторе возвращается первоначальный результат.
Сообщение и событие outbox записываются одной транзакцией. Потребитель outbox может
получить событие повторно: `event_id` обеспечивает дедупликацию на клиенте/воркере.
После удаления сохраняется минимальная запись дедупликации без текста, пока существует
диалог; старый повтор не должен воскресить сообщение. Для удалённой пары все записи запрещены.
Счётчик `seq` пары выдаётся транзакционно; время клиента не определяет порядок.

## Realtime и офлайн

Realtime является ускорением, а не единственным источником данных. После разрыва
соединения клиент запрашивает sync; пропущенные/повторные/неупорядоченные события допустимы.
Транспорт выбирается в архитектурном ADR; подписка авторизуется по сессии и текущей
паре, с немедленным закрытием после отзыва членства. Публичные каналы запрещены.
Клиент хранит курсор только после атомарного применения всей порции событий.
При сбросе курсора выполняется повторная загрузка, сохраняя только валидную локальную очередь.
Кэш и очередь разделены по `user_id`, `couple_id`, `membership_epoch`.
Нативный приватный кэш шифруется проверенной библиотекой, ключ находится в Keychain/Keystore;
SecureStore хранит ключ/малые токены, а не всю историю. Смена аккаунта очищает кэш и ключ.
После полного выхода неотправленные тексты удаляются с предварительным предупреждением.
Офлайн нельзя доказать актуальность членства: старый кэш может оставаться на уже
авторизованном устройстве до соединения. Нельзя обещать дистанционное стирание офлайн-копий.

## Квитанции и приватность

По умолчанию отметки прочтения выключены; пользователь включает их сам.
Включение действует на будущие события, не публикует задним числом историю чтения.
Публичное чтение хранится по message_id, не cumulative read_seq: чтение нового сообщения
не отмечает старые как прочитанные. Сервер фиксирует receipt_epoch при включении;
отложенные квитанции предыдущей эпохи отвергаются. В API передаётся текущий receipt_epoch.
«Доставлено» означает сохранение хотя бы одним авторизованным устройством получателя;
«Прочитано» означает подтверждение активного экрана при разрешённой настройке.
Внутренний личный курсор для прокрутки не раскрывается партнёру при выключенных квитанциях.
Индикатор набора, если добавлен, имеет короткий TTL, не сохраняется в истории;
статус «был в сети» и геолокация не входят в P0.

## Push и «Думаю о тебе»

Push по умолчанию нейтрален: «Новое сообщение», без текста, имени пары и фото.
Токен устройства принадлежит конкретной сессии пользователя; выход отзывает привязку.
Перед отправкой воркер заново проверяет получателя, членство, удаление сообщения,
настройки и тихие часы. Повтор задания не создаёт серию одинаковых уведомлений.
Push может запаздывать или не приходить; чат работает независимо от него.
«Думаю о тебе» создаёт отдельное идемпотентное событие, с ограничением частоты
(предложение: одно push не чаще раза в минуту), и не раскрывает статус партнёра.
Пульсация отключается при системном reduced motion; нажатие не показывает успех до сохранения.

## Разрыв пары, экспорт, удаление

Ниже техническое предложение, не принятое решение о судьбе общего архива.
До реализации требуется ADR владельца: сохранение архива у каждого либо закрытие доступа
с экспортом; до согласования нельзя запускать удаление общего архива в production.
Независимо от решения любой участник может немедленно прекратить новое общение.
Предлагаемый вариант закрытия: сервер атомарно закрывает
пару и отзывает оба активных членства, realtime, новые приглашения, задачи и отправки.
История больше не доступна обычным API; новая пара всегда имеет новый ID.
Перед подтверждением показать последствия и возможность заранее экспортировать общую
видимую историю. Экспорт исключает черновики и запечатанные письма другого человека.
Не блокировать немедленный выход ожиданием экспорта или действий второго участника.
Удаление аккаунта удаляет его токены/кэш, закрывает пару и запускает удаление данных.
Окончательные сроки удержания и правовая политика должны быть утверждены до пилота;
техническое предложение: закрытая пара помещается в недоступную очередь удаления,
активные данные удаляются до 30 дней, резервные копии истекают до 90 дней.
Восстановление бэкапа обязано повторить журнал удалений до открытия доступа.
Экспортированные файлы, скриншоты и копии другого участника отозвать невозможно.

## Приёмка

- Две пары и посторонний пользователь: нельзя читать/отправлять/редактировать/скачивать чужое.
- Повтор POST сообщения 20 раз и таймаут после COMMIT дают ровно одно сообщение.
- Отдельный повтор команды заботы даёт ровно одно событие заботы, без дублирующих push.
- Параллельные устройства, смена сети, перезапуск, истечение сессии, пропуск событий не теряют текст.
- Отзыв членства между проверкой и COMMIT не допускает отправку; тест гонки обязателен.
- Повторное приглашение и смена партнёра не открывают прежний диалог/локальную очередь.
- Нет раскрытия текста в push, логах, crash-report, аналитике и уведомлениях на экране блокировки.
- Удаление скрывает текст и цитаты; устаревшее редактирование/повтор отправки его не возвращает.
- Включение/выключение read receipts не раскрывает старые чтения; отложенная старая эпоха отвергается.
- RU/EN, экранная клавиатура, большие шрифты, screen reader, reduced motion, длинный текст проверены.
- Сквозной тест на iOS/Android с двумя аккаунтами, затем с четырьмя аккаунтами двух пар.
- Coverage ≥90% по lines/functions/branches/statements всего собственного runtime-кода,
  включая неимпортированные файлы; независимая приёмка точного коммита.
- Нагрузочная цель для пилота: 100 одновременных соединений, p95 server ack ≤1 секунды
  в тестовом регионе; это критерий теста, не публичная гарантия/SLA.
- Без реальных тестов сервера, БД и устройств разрешено говорить только «прототип».
