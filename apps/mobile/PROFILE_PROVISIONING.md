# Explicit synthetic profile provisioning

Status: implemented; author checks passed; independent review pending. No publication or production use.

An authenticated provider account can now explicitly create its own domain profile from the unmapped test screen. Sign-in and context discovery never auto-provision. The UI shows a localized RU/EN “Create test profile” action only in unmapped state or after an uncertain, retryable profile result. Existing Kimi styling, navigation and heart are unchanged. The default App still has no networking.

The server composition defaults enableSyntheticProfileProvisioning to false. Enabling it requires a loopback baseURL. The isolated test server must opt in; production origins cannot enable this flag. No environment fallback, migration/backfill, external account creation, email delivery, invitation or pair creation is introduced.

## Request and SQL outcome

POST /v1/profile accepts only application/json with the empty object {} and no query selectors. Provider/domain/pair IDs are never taken from client input. The same verified official cookie session and PostgreSQL authority determine ownership. Successful JSON is {ok:true,value:{sessionId,userId,created}}, with 201 for creation and 200 for an already-existing live profile. userId is generated by PostgreSQL; sessionId is a nonsecret binding, not a credential.

The server inserts users and better_auth_identities in one transaction, protected by the unique provider identity mapping. It does not upsert or reassign an existing mapping and does not resurrect a mapped deleted domain user. Concurrent requests, including separate sessions for the same provider account, serialize on the provider-user lock. If a mapping appears while that lock is awaited, a bounded read-only retry restarts with the domain-user-first lock order. A failed insert rolls back both new rows. Unknown commit outcomes are not retried automatically by the server.

401/403 invalidates the client session. 400/404/409 disables the profile action; this includes disabled server support or unavailable/deleted mapping. Network failures, 5xx or malformed acknowledgements are treated as uncertain results with a safe explicit retry. No claim of rollback is made merely because a response was lost.

## Client session and cancellation rules

Before the mutation, the controller reads context using the exact captured official cookie and requires its sessionId to match the verified sign-in identity. The same cookie snapshot is then used for POST. A different account/session that replaced stored cookies cannot silently receive the mutation. If the preflight discovers a profile already exists, no additional POST is needed.

After a valid acknowledgement, the client discards its fields as authorization inputs and rediscovers authoritative context. Normally that becomes no_active_pair: a profile exists, but chat access still requires an active pair. A later explicit waiting-space step is documented in WAITING_SPACE.md. This does not complete signup or pairing.

Provisioning runs outside the serialized auth mutation queue. Logout/cancel increments generation, aborts current networking and clears visible state immediately; any late profile/context response is ignored. Cancellation cannot undo a database transaction that already committed. A later login/discovery or explicit retry observes the actual state. Duplicate clicks while busy do not start extra mutations.

No profile fields, message bodies or drafts are persisted locally by this feature. Cookie storage remains owned by the official origin-bound Expo/SecureStore plugin.

## Tests and limits

Tests cover explicit-only behavior, empty body/ownership, concurrent idempotency, separate-account isolation, deleted mapping, rollback, revocation races, lost acknowledgement, cancellation and stale callbacks. The real mobile controller → loopback HTTP → PostgreSQL case creates a domain profile without injecting any client identity mapping or provisioning it through a fixture, then proves there is still no pair/chat access.

Native I/O is mocked in unit tests. Real SQL scenarios use the official Node auth client fixture, not a device's Expo/SecureStore runtime. iOS/Android Metro/Hermes export is bundle evidence only. Native build/device/two-device verification and production operation remain unverified. Dependencies are unchanged; previous audit findings remain unresolved.

Current evidence is in evidence/profile-provision. Run the same mobile/API typecheck, lint, test, safety, PostgreSQL and export commands documented for the preceding stage. No coverage thresholds were relaxed.
