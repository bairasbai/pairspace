# Explicit synthetic invitation issuance and revocation

Status: implemented; independent acceptance pending. This checkpoint is API-only, loopback-only and synthetic. It issues and revokes an opaque invitation token but provides **no acceptance route, partner activation, delivery, email, push, mobile UI or production onboarding**. An issued token cannot yet be used to join a pair. No production service, account or data is touched.

## Enablement and perimeter

`createApiApplication` accepts optional `enableSyntheticPairInvitations?: boolean`. Omitted/false means the route is absent (404), regardless of environment variables. True requires explicit loopback baseURL host `127.0.0.1`, `[::1]` or `localhost`. Non-boolean values are rejected. This flag is independent of profile provisioning and waiting-space creation; enabling it enables neither prerequisite endpoint.

`/v1/spaces/waiting/invite` accepts GET, POST and DELETE, with 405 and `Allow: GET, POST, DELETE` for other methods. Every accepted method passes the composed byte/read-deadline bounds. All requests require exact trusted Origin, or Expo-origin only when Origin is absent. Authentication uses the official current Better Auth cookie, caching disabled, then authoritative session rechecks. Bearer fallback is forbidden. All responses have no-store and nosniff. The host must not log cookies, invitation tokens, request/response bodies or SQL parameters.

The domain user and waiting couple are selected exclusively from the verified session and current server-side membership. Query parameters are rejected. The endpoint never accepts a caller-selected user, provider, session, couple, slot or epoch. A live mapped profile and exactly one active waiting membership, this user in slot 1, are mandatory. No profile or waiting space is implicitly created. Active/closed/inconsistent spaces and deleted profiles fail closed even for historical-command retries.

## Exact HTTP contract

Success is `{ok:true,value:...}`. Invitation metadata is exactly:

`{id,commandId,status,createdAt,expiresAt,revokedAt,consumedAt}`

All IDs are UUID strings and all dates are UTC ISO strings; revokedAt/consumedAt can be null. Status is `pending`, `expired`, `revoked` or `consumed`. No token hash, issuer/consumer identity, pair ID or provider session ID is included.

- GET has no body, nonzero body declaration or Transfer-Encoding. 200 value: `{state:'current',invitation:metadata|null}`. It reads only the caller's current unrevoked/unconsumed invite. An expired row remains visible as expired until explicitly revoked or replaced. It never returns a token.
- POST requires application/json and exactly `{commandId:UUID}`. First successful issuance: 201 value `{state:'issued',invitation:metadata,token:string}`. The token is generated by Node `crypto.randomBytes(32)`, encoded unpadded base64url (43 characters). Only its SHA-256 hex digest is persisted.
- Same POST command in the same own waiting couple: 200 value `{state:'replayed',invitation:metadata,token:null}`. Repeating a command never recovers a token or issues another one, including after expiry or revocation. The schema can represent consumption for future acceptance; after activation this endpoint instead rejects the now-active couple. No post-activation replay is promised.
- Different POST command while a pending invite exists: 409 `invitation_exists`. If the current invite is expired, it is revoked and a new invite is inserted atomically. There is no silent live-token rotation.
- DELETE requires application/json and exactly `{inviteId:UUID}`. This is an expected-version selector, scoped strictly to the caller's derived waiting couple, never an authorization grant. Matching own pending/expired invite: 200 value `{state:'revoked',revoked:true}`. Matching already-revoked historical invite: 200 value `{state:'revoked',revoked:false}`. Repeating an old revoke never revokes a replacement. Missing, foreign or consumed ID: generic 409 `invitation_unavailable`.

UUIDs are normalized to lowercase. Whitespace and Content-Type charset parameters are accepted. Additional keys and empty/non-object/malformed JSON are rejected. POST/DELETE require the same media and request bounds. GET accepts no selectors and performs no mutation.

Error bodies are `{ok:false,error}`:

- 400 `invalid_request`: invalid query, body, JSON/UTF-8 or body declaration. Bounded oversized/stalled reads retain 413/408; the Node adapter may close a stalled socket instead.
- 415 `unsupported_media_type`; 405 `method_not_allowed`; disabled/unknown route 404 `not_found`.
- 401 `unauthenticated`: missing/expired/revoked official session, failed authoritative ownership/time recheck.
- 403 `forbidden`: composed origin perimeter.
- 409 `profile_unavailable`: absent/deleted/missing mapped profile or changed mapping.
- 409 `space_unavailable`: absent own waiting membership, changed membership, active/closed couple or invalid own waiting slot shape.
- 409 `invitation_exists` or `invitation_unavailable` as above.
- 503 `temporarily_unavailable`: unexpected errors, missing migration, malformed/ambiguous database rows or uncertain transaction result. No provider/SQL/token detail is returned.

## Transactions, expiry and lost acknowledgement

Lock order: domain user FOR UPDATE → provider user/session FOR SHARE → mapping FOR SHARE → couple FOR UPDATE → invitation rows FOR UPDATE. The initial mapping/membership reads discover candidates only. After locks the mapping and membership must still match; never follow a replacement identity or couple. The waiting shape uses counts and an own-slot count, not another member's identity.

Session time is rechecked after mapping and couple locks, and again after all invitation locks. `lockedBetterAuthSessionTime` returns the same fresh PostgreSQL clock timestamp that validated the exact owner-matching session and its original verified expiry. That timestamp determines invitation status, revocation time, creation time and expiration exactly 600,000 ms later. A request that waited beyond session expiry cannot issue/read/revoke. A stale pre-lock application clock cannot extend the TTL. The existing boolean recheck helper delegates to this shared check, preserving other routes' behavior.

Every mutation is one transaction. Expired revocation and replacement insertion commit together. Missing/malformed mutation acknowledgements throw and force rollback; there is no UPSERT, orphan cleanup or automatic retry on uncertain outcomes. Current-row and historical-target locks ensure a concurrent revoke cannot create an inconsistent replay snapshot. Future membership/status/acceptance writers must follow the reviewed lock protocol; direct fixture SQL is not an exposed product operation.

The raw token is returned **only in the first 201 response**. A lost HTTP acknowledgement or lost COMMIT acknowledgement can leave the caller unable to recover it. The server never caches, logs, encrypts for recovery or reissues that token. Recovery is explicit: GET current metadata, DELETE that exact invite ID, then POST a fresh command ID. A repeat of the original POST only returns metadata and token:null. A retry of an older DELETE cannot destroy a newer invite created by another session. GET null means no current invite, not proof that a prior command never committed. Historical command uniqueness survives revocation and expiry.

## Migration and retained limitations

Apply `migrations/004_pair_invites.sql` transactionally after existing domain migrations in the same trusted schema as Better Auth. The factory does not run migrations. `pair_invites` contains:

- UUID primary key, couple FK and composite issuer membership FK.
- Unique `(couple_id,command_id)` and globally unique 64-character lowercase SHA-256 digest.
- A partial unique current invite per couple where both revoked_at and consumed_at are null. Expiry alone does not release it.
- Finite timestamps, expiry after creation, non-backdated revoke, mutually exclusive consumed/revoked states, consumed timestamp/consumer presence equivalence, and valid pre-expiry consumption time.
- A composite consumer membership FK and issuer/consumer inequality for future acceptance compatibility. A future acceptance transaction can insert the second member then mark consumption. These constraints are not an acceptance implementation or authorization policy.

No raw-token column, recipient contact, delivery queue, notification, membership mutation or activation handler is added. Profile, waiting creation, context and chat contracts remain unchanged. Waiting chat is still denied. Production migration management, grants/RLS, abuse/rate limiting, token delivery/acceptance, unpairing/retention, native-device checks and independent security review remain separate stages. Dependencies and lockfiles are unchanged.
