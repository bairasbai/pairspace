# Explicit synthetic waiting-partner space

Status: implemented and author-verified; independent acceptance pending. This is a loopback-only synthetic runtime slice, not production onboarding, a deployed service, invitation acceptance or completed pairing. No production data, credentials, external services or schema were changed.

## Domain and access

The existing schema already supports `couples.status='waiting_partner'`. Creating a space inserts one waiting couple and its creator's `couple_members` row with `slot=1,status='active'`. Here active membership means a live/reserved slot. It does **not** mean that the couple is active or that chat is allowed. The existing partial unique index `one_active_couple_per_user` prevents the same domain user holding another live slot. The existing deferred triggers still require exactly two active members for an active couple.

No migration is needed. Chat authorization is unchanged: it independently rechecks the official session, identity, pair status, current membership and epoch. Waiting spaces cannot send/read chat even with a correct couple ID and epoch. No partner, invitation, token, activation, message, outbox event or notification is created by this endpoint.

## Opt-in and HTTP contract

`createApiApplication` accepts optional `enableSyntheticWaitingSpaceCreation?: boolean`. Omission/false returns 404 for this route, regardless of environment variables. True is allowed only with explicit loopback baseURL host `127.0.0.1`, `[::1]` or `localhost`. Invalid non-boolean flags are rejected. This flag is independent of `enableSyntheticProfileProvisioning`: enabling one does not enable the other. Construction does not create a listener or domain rows.

`POST /v1/spaces/waiting` accepts `Content-Type: application/json` and exactly the empty JSON object `{}`. Whitespace and charset parameters are accepted. Any query parameter, user/provider/session/couple ID, slot, epoch or extra field is rejected. Other methods return 405 with `Allow: POST`. Existing request byte/time limits and exact trusted Origin, or Expo-origin only when Origin is absent, remain in force. Authentication requires the current official Better Auth cookie with cookie caching disabled; Authorization headers cannot supply a fallback identity.

Responses contain only the caller's server-selected domain identifiers:

- First creation, 201: `{ok:true,value:{sessionId,userId,coupleId,membershipEpoch:1,created:true}}`.
- Existing valid own waiting space, 200: `{ok:true,value:{sessionId,userId,coupleId,membershipEpoch,created:false}}`.

`sessionId` is the nonsecret provider session ID, never its token. The user must already have a live mapped domain profile; this action never provisions or reassigns one. `coupleId` is generated by PostgreSQL `gen_random_uuid()`. No other member's ID or data is returned. All responses use no-store and nosniff.

Error contract:

- 400: query/body selectors or malformed JSON; 415: unsupported media type; existing bounded body errors retain 413/408 behavior.
- 401 `unauthenticated`: absent/expired/revoked official session or failed authoritative recheck.
- 403 `forbidden`: composed origin perimeter.
- 409 `profile_unavailable`: absent mapping, missing/deleted mapped profile, or an observed changed mapping.
- 409 `space_unavailable`: existing active couple, closed couple with live membership, invalid waiting-member shape, or membership changed while locking.
- 503 `temporarily_unavailable`: unexpected failures or ambiguous/malformed database data. No SQL/identity/provider error detail is exposed.

A network failure/503 can have an uncertain commit outcome. The server does not blindly retry it. A later explicit POST returns the committed waiting space rather than inserting another one; context can also rediscover it.

## Transaction and idempotency

1. Official getSession verifies the cookie. Discover a candidate domain mapping without locks; reject absent or ambiguous/malformed results.
2. Lock the existing live domain user `FOR UPDATE`. This serializes creation across distinct provider sessions of the same user, not merely requests sharing one session.
3. Lock/check the provider user and exact owner-matching session `FOR SHARE`, then check authoritative creation/expiry against PostgreSQL clock_timestamp().
4. Reread mapping `FOR SHARE`; it must match the original user. Never switch identity after taking locks. Recheck session time after this potentially contended mapping lock.
5. Discover the user's active membership. If present, lock its couple `FOR UPDATE`, reread membership in a fresh READ COMMITTED statement and recheck authoritative session time after the couple lock. Require a valid epoch, waiting status and exactly one active member: this same user in slot 1. Only counts and an own-slot count are selected for validation, not other user IDs. Return the existing waiting space without writes. An active/closed/inconsistent space blocks creation without cleanup, reassignment or bypass.
6. If there is no active membership, recheck session time and insert a server-UUID waiting couple at epoch 1, then its creator's active slot 1. Both writes commit atomically. Any failed/invalid insert rolls back the couple too. There is no UPSERT or automatic orphan cleanup.

Lock order is domain user → provider user/session → mapping → couple → membership. Later session rechecks reacquire locks already held; they introduce no new resource order. Revocation completed before the session lock prevents creation. If creation holds that session lock first, official revocation waits for commit, then future requests are denied. Mapping/couple lock waits crossing expiry fail closed. All future membership/status writers must respect the same locking protocol; direct fixture SQL is not an exposed product operation.

The schema has no historical-membership tombstone rule preventing future space creation after all memberships are revoked. This endpoint neither implements unpairing nor changes retention. Unsupported mapping changes and incomplete closed/live states are rejected when observed; no production lifecycle policy is implied.

## Session context

`GET /v1/session/context` adds `{state:'waiting_partner',sessionId,userId,coupleId,membershipEpoch}` only for the validated own single-slot waiting shape. Invalid waiting shapes return opaque 503, never ready or no_active_pair. This is a discovery snapshot, not a chat authorization grant. Existing unmapped/no_active_pair/ready semantics are preserved, including closed pairs returning no_active_pair. Context rechecks the authoritative session again after mapping/couple lock waits before returning any successful snapshot.
